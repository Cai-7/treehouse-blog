复现 CellFlow（见[《把 CellFlow 从 JAX 搬到 PyTorch》](/posts/cellflow-pytorch-alignment)）时，PyTorch 版一个 split 要跑几个小时，JAX 原版参考只要 72–74 分钟。每个 batch 都要解一次 Sinkhorn（熵正则的最优传输），它最可疑。

这篇是那次排查的复盘。结论先放前面：**一个函数单独测快了，不代表整个训练循环会变快；而我最初对“为什么慢”的几个判断，有一半是错的。**

## 先把“慢多少”测对

第一个错误出在计时上。Lightning 进度条显示的耗时是 14 分钟、33 分钟，看起来不算太慢。但训练开了梯度累积（每 20 个 micro-batch 才更新一次参数），进度条混着两种步数在算，显示的时间根本不是真实耗时。

改用进程外部的开始、结束时间戳之后，一个 fold 实际要 **3.5–5.4 小时**。

第二个错误是比较对象。拿来对比的那几次 JAX 跑 72–74 分钟，用的是 $\epsilon = 1.0$；而我的版本是 $\epsilon = 0.1$。$\epsilon$ 越小，Sinkhorn 收敛越慢，所以这本来就不是同配置的对比。

还有一次出现了将近 10 倍的慢：两个 fold 同时在两张 GPU 上跑，但它们的 Sinkhorn 都在 CPU 上解，抢的是同一颗 CPU 的线程和内存带宽。

## 配置为什么一改就慢了

| 项目 | 原来的 veloFM | 对齐 CellFlow 后（v3） |
| --- | --- | --- |
| `epsilon` | 0.05（绝对值） | 0.1（相对，代价矩阵先除以均值） |
| 停止条件 | 固定 200 次迭代 | 误差小于 1e-3，最多 1000 次 |
| 每次 Sinkhorn | 约 200 次 × 50 ms | 约 600–1000 次 × 140 ms |
| 一个 fold | 约 1 小时 50 分 | 约 3.5–5.4 小时 |

算法没变，变的是停止规则和有效的正则强度。再加上原来的实现是在 GPU 上算好代价矩阵，拷到 CPU 用 NumPy 版的 POT 解，再把结果拷回 GPU。迭代次数一多，这条来回拷贝的路就全暴露出来了。

## 三种提速尝试，单独测都很快

所有数字都是 A100、1024×1024 的代价矩阵：

| 实现 | 单独调用耗时 | 放进训练后 |
| --- | ---: | ---: |
| POT，CPU（基准） | 91–144 ms | 约 14–18 it/s |
| 自己写的 log-Sinkhorn，GPU，fp32 | **1.6 ms**（4 次迭代收敛） | 约 18 it/s |
| `torch.compile` 包装的固定迭代版 | 7.5–12.4 ms | 约 9.9 it/s |
| POT 的 torch GPU 后端 | 约 4 ms | **约 6.8 it/s，比 CPU 还慢** |

单独测，GPU 版比 CPU 快了 86 倍（138 ms → 1.6 ms），数值和 POT 的差异在 1e-10 量级。可一放进训练循环，吞吐量几乎没变，有的版本反而更慢。

过程中还修了一个精度问题：Lightning 开着 `bf16-mixed` 时，代价矩阵是 bf16，log-Sinkhorn 因为精度不够要多迭代好几次才收敛。在求解器内部强制用 fp32 之后，又回到 4 次就收敛。

## 我最初的解释是错的

一开始我以为：CPU 上解 Sinkhorn 的同时，GPU 在做前向和反向，两边是**重叠**的，所以 Sinkhorn 再快也省不了多少时间。

回到代码里逐行对调用顺序，发现根本没有重叠。`coupler.couple(...)` 完全结束之后才调用模型；POT 那一步还要先 `.cpu().numpy()`，这会让 GPU 先停下来同步。真实的执行顺序是串行的：

```text
GPU:  算代价矩阵 ─同步/拷贝─ 等 CPU 解完 ─拷回结果─ 前向 ─ 反向
CPU:                       POT Sinkhorn
```

所以总耗时是几段**相加**，不是取最大值。

那为什么 GPU 版放进训练还是不快？在训练里实测，那次 1.6 ms 的调用变成了约 11.7 ms。可能的原因有 autocast 和图断点、每一步的 Python 调度开销、和大 MLP 抢同一个 GPU stream，以及梯度累积下的计时误差。这些还要用同步的分段计时来确认，不能再凭直觉解释。

## JAX 快在哪

OTT-JAX 用的也是同一个 log 稳定的 Sinkhorn，算法上没有优势。快在交付方式：

- `jax.jit` 把整个 Sinkhorn 编译成一个 XLA 程序；
- 迭代用 `lax.while_loop`，每一轮不经过 Python；
- 匹配函数和梯度更新都是编译好、常驻在设备上的。

PyTorch 这边是 eager 的 Lightning 训练步，加上一个单独尝试编译的 Sinkhorn，中间到处是图断点。

## 后来是怎么解决的

排查时还发现了几处和 OT 无关、但白白浪费时间的地方：

- 同一个条件的 token 被复制成 1024 份再编码，而 JAX 只编码一次，dropout 之后再广播；
- 条件编码器用的是 1024 维的标准多头注意力，CellFlow 默认是 8 个头、总共 64 维的 qkv；
- 基线根本用不到 velocity，数据里却把它也加载了进来。

在下一个版本（v4）里，我把条件编码器对齐原版、去掉多余的 velocity 加载，并把数值等价的 Sinkhorn 整个放到 GPU 上，不再经过 CPU 和 NumPy。一个 split 的训练从约 4 小时降到 **53 分钟**，单次 Sinkhorn 从约 170 ms 降到约 2.4 ms。后面几轮对齐之后又降到 48 分钟左右，不比 JAX 慢。

## 这一趟学到的

- **先把计时测对。** 梯度累积下的进度条耗时不可信，要用进程外部的时间戳，最好再加同步的分段计时。
- **对比之前先对齐配置。** $\epsilon$ 不一样，速度对比就没有意义。
- **微基准测快了，不等于端到端变快。** 真正的瓶颈常常在函数之间：数据来回拷贝、同步、调度。
- **先读清楚代码的执行顺序，再解释现象。** “重叠所以没提速”听起来很合理，却和代码对不上。
